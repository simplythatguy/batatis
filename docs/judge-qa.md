# Batatis: The 23 Hardest Judge Questions

*Prepared for Submission 1 (Oct 29, 2026). Status is as of Oct 22, 2026. Where we do not know something, the answer says so and names what would measure it. Evaluation figures are model-checked and mostly in sample, and none is human-verified. Status words follow the Implementation Plan, §3: **built**, **backend** (the API is merged and its screen is not finished) and **roadmap**. When a judge asks which AI vendors we use, the answer is "third-party AI providers, under their standard API data terms", and the vendors are not named in public materials.*

**1. If Batatis gets something wrong and a variance is issued, who is liable?**
Batatis never states that a design complies or is safe. It checks whether an application is complete and cites the code. The decision stays with the safety codes officer (SCO), who acts for the authority having jurisdiction. The Council says that authority is the accredited organization, with SCOs exercising delegated powers ([IB-2026-10-16](https://ebs.safetycodes.ab.ca/documents/webdocs/SR/IB-2026-10-16_AHJ_Clarification.pdf)). The Council also says that registration in its portal is not approval and does not move responsibility for the decision ([IB-2026-10-01](https://ebs.safetycodes.ab.ca/documents/webdocs/SR/IB-2026-10-01%20Orders%20and%20Variances%20Registration%20Changes.pdf)). Our officer screen says "Accepted as administratively complete" and adds that this is not an approval of the design. Our product terms with any organization would say the same, and a lawyer has not reviewed them yet.

**2. How accurate is it?**
We have four measurements, each with its limit, and one gap.

- **Intake rules,** on 60 development cases: typed-fact precision 159/159 and recall 159/162. In sample, because we wrote the labels while we wrote the rules.
- **Engineer-needed flag,** on the same 60 cases: it agrees with model-written labels on 50 and sends 27 to the applicant as unknown. It never answers "no" on these text-only cases, so zero under-flags holds by construction.
- **Relevance stage,** on 53 public Alberta precedents: it put a cited article first in 64% of cases and in the first five in 81%. Keyword search got 32% and 66%. This run had no verifier stage, covers one province and one code, and the gold lists can be incomplete.
- **Package review,** on synthetic forms: tests plant defects from 16 classes and check that the review names each one. We wrote the tests with the checker, and they are not a blind evaluation.
- **Gap:** the final code identification pipeline is not measured. The benchmark is in draft PR #58 with two draws of the relevance stage complete. A third draw and a latency pass need account credit.

All labels are model-checked. No human-verified subset exists. Sources: `evals_dev/intake_facts/score.py`, `evals_dev/section_d_flag/RESULTS.md`, `docs/research/2026-10-20-vision/README.md` §6, `engine/tests/test_package_review_planted.py`.

**3. What stops it from inventing a code citation?**
The verifier keeps a citation only if its quote matches the article's text in our database word for word. Otherwise it is dropped, and the pipeline checks again before display. A property test shows that a deliberately lying model produces zero fabricated ids or quotes on screen. Section C objectives and functions come from the code's attribution tables, not from generated text. When a sentence has no row, the screen says so. Code search shows database rows only. We do not yet know how often a correct article is dropped by this rule. That rate is part of the unfinished benchmark.

**4. What does it cost to run per application?**
The model cost of one identification run is about US$0.019 to US$0.020, or C$0.027 to C$0.028. That is measured: the relevance screen of all 2,080 articles is US$0.0173, the re-rank US$0.0006 and the verifier US$0.001 to US$0.0017. The optional intake model pass is about US$0.0006 a call. An assistant answer costs at most about US$0.006 under an input-size assumption. With stated usage, one application costs about US$0.05 (typical) to US$0.12 (generous). The Section C lookup, completeness checks, package review and form export call no model. Hosting, support and pack upkeep are not priced, and the demo runs on a free tier. Each call reserves its worst-case cost first, and a daily cap (default US$5) and per-IP limits apply. When the cap or a model stage is unavailable, the product falls back to a labelled keyword search. Sources: `docs/business-plan.md` §6, `docs/research/2026-10-21-source-checks.md` §5.

**5. Why would an officer open it twice?**
We do not know yet, because no officer has used it. The built part is a queue with claim, a paper sheet of the application beside its completeness list, messages, and an accept-or-return decision. The package review, which is a backend, reads any completed SCC form with its attachments, so it works on applications not made with Batatis. It drafts an information request in which every item is a question to the applicant, and after a re-upload it shows how many gaps were resolved. Whether this saves time would be measured with our planted-gap protocol: the same package reviewed with and without the report, timed, counting the gaps caught. That protocol has not run.

**6. How does this fit the Council's new portal?**
From Dec 1, 2026 the Orders and Variances Portal is the only way to register variances. Only SCOs can register, each variance is registered for a specific location, and the revised variance form and the supporting documentation must be included ([IB-2026-10-01](https://ebs.safetycodes.ab.ca/documents/webdocs/SR/IB-2026-10-01%20Orders%20and%20Variances%20Registration%20Changes.pdf)). Batatis fills that revised form. From Dec 1 a variance must be registered "at the time of issuance or as soon as reasonably practicable thereafter", and the emailed copy ends. Before that, the Council's earlier bulletin ([IB-2025-11-18](https://ebs.safetycodes.ab.ca/documents/webdocs/SR/IB-2025-11-18%20Mandatory%20Documentation%20of%20Variances.pdf)) asks for a copy within 10 days of issuance. Our close-out record, which is a backend, lists what to send and what to keep and shows a due date 10 days after the decision. It does not follow the portal's timing yet, and changing that is planned before Dec 1. The officer registers, and Batatis never does. Registration is not approval. The Council says high-volume organizations may work with it on approved integrations and that technical requirements will follow, so any direct integration waits for them.

**7. Where does applicant data go, and which privacy law applies?**
The demo runs on Vercel with its database in the US East region, and third-party AI providers process text in the United States under their standard API data terms. Before any AI call the app makes, Batatis removes the names, contact details and addresses it recognizes. It recognizes known case values, account names, contact phrasing, email addresses, phone numbers, street addresses and postal codes. An unrelated name typed with no context can still pass, which is why the notice says "recognizes". Cases and their files are deleted 7 days after creation, or sooner on request. For private applicants Alberta's PIPA applies, and the federal Privacy Commissioner says PIPEDA can still apply to a disclosure across provincial or national borders, case by case. For municipalities the Protection of Privacy Act applies. A pilot contract would set who is responsible for what and who owns the pilot records, subject to the organization's own privacy review. A pilot would use Canadian-region hosting, and it would use the model path only if the organization's own privacy review approves it. Sources: `docs/deploy.md`, `docs/api/accounts-review.md`, `docs/implementation-plan.md` §5, `docs/research/2026-10-21-source-checks.md` §2b.

**8. Can you legally use the building code text?**
The app shows code text in full, with its citation, PDF page and a credit and link to the National Research Council's publication, and the code library lets a user read any article. The code in force is the NBC(AE) 2023, 2nd printing. NBC(AE) 2023 says commercial reproduction of National Research Council material needs written consent. We have not asked for terms, and written terms are a gate before any public commercial launch. If terms were refused, the fallback is a link-out and user-supplied-text design (`docs/research/2026-10-20-vision/C-market-provinces-business.md` §3.2).

**9. Does this only work in Edmonton or Calgary?**
The provincial form and process notes work anywhere in Alberta. Jurisdiction packs, which are data, exist for Calgary, Edmonton and a fallback for any other Alberta office. Today an applicant can submit in the app only to Calgary or Edmonton, and reviewer accounts exist only for those two authorities. Calgary also asks for its own Request for Specific Variance form, and exporting that form is roadmap. Alberta has 433 accredited organizations, and the packs reach them through the fallback until an office gets its own pack. Every other province is a labelled "preview" with neither the adopted code nor a pack, so another province needs a form map, a code edition and a reviewed pack that we have not built.

**10. Who are your competitors?**
Code-search and plan-check products such as UpCodes, CodeComply.Ai, Archistar, Clariti's CivCheck and GreenLite check ordinary permits against prescriptive rules, zoning or completeness. None of their public pages describes preparing or reviewing alternative-solution applications. At least six Canadian municipalities launched AI pre-check tools between March and September 2026, all for zoning, completeness and Part 9, so well-funded vendors already hold those relationships and could add an alternative-solution module. The real status quo is code consultants preparing these files by hand, and an official template and guide that the Council and SSRIA are developing, which we would fill rather than fight. Our "nobody does this" claim rests on web search and vendor pages on Oct 20, 2026, so it is absence of evidence, not proof. Source: `docs/research/2026-10-20-vision/C-market-provinces-business.md` §1.

**11. Who pays, and how much?**
The applicant pays, and the officer's tier is free in Alberta. Our first buyer hypothesis is production homebuilders and the consultants who prepare their files, because the applicant writes the Division C documentation, which is now mandatory ([IB-2025-11-18](https://ebs.safetycodes.ab.ca/documents/webdocs/SR/IB-2025-11-18%20Mandatory%20Documentation%20of%20Variances.pdf)). The price to test is C$150 to C$750 per completed package and about C$2,400 a year for a repeat filer's seat. Both are assumptions with their basis in `docs/business-plan.md` §5.2. No buyer has seen a price. Calgary and Edmonton charge no variance fee, so an authority has no fee income to pay a tool from. Willingness to pay would be measured with price tests during a pilot.

**12. Will anyone adopt it, given that some variances are repeats?**
That is a real risk. The Council's Data Hub shows that a few Part 9 articles dominate, and Calgary already turns the most common one into a standing posted variance. The Data Hub does not show variance type, and the Council does not collect supporting materials, so how many entries are bespoke is not published. The research assumes 5% to 15% (an assumption). If fewer than 300 bespoke variances a year appear in Alberta, our own kill criterion says to pivot to standing-variance workflow and all-permit completeness. Coded rules for the most-varied articles exist as an unreviewed backend with no screen, and standing-package checklists for the repeats are roadmap.

**13. Why can't a better general-purpose AI model replace you next year?**
A better model improves anyone's code search and drafting, including ours, and lowers our cost. It does not supply jurisdiction packs that are researched and kept current, a place in the officer's workflow that is earned authority by authority, or an exact core in which citations can be checked against a code database. Officer corrections collected in a pilot, under a data agreement with the organization that owns its records, would add to that. We pin model versions and have a benchmark harness so that we can swap a model and compare it on the same cases.

**14. Has anyone actually used it?**
No. No applicant, officer or pilot partner has used Batatis, and no pilot partner has agreed to anything. What exists is automated tests, an agent-run browser walk of the applicant and officer flow, and the evaluations in question 2. Human sessions are written as a protocol with targets and begin only if a sponsor engages.

**15. What happens after Demo Day?**
The target is a pilot, run in parallel with one accredited organization, in the program's Dec 2 to Mar 2 implementation window, which the program says is "not guaranteed" ([onboarding guide](https://edmontonunlimited.com/wp-content/uploads/2026/09/Built-World-Challenge-Onboarding-Guide.docx.pdf)). A pilot needs Canadian-region hosting, privacy terms the organization approves, and a scope under the C$75,000 open-tender threshold that Calgary applies (`docs/research/2026-10-20-vision/C-market-provinces-business.md` §5.2). Success targets are fewer returns for more information than the organization's baseline and an officer review time below the manual baseline. If no organization engages, we keep building the applicant side.

**16. The brief asks for Appendix 1. Why does your export fill the Council's form instead?**
Since the brief was published, the Council has replaced the template with a form dated Oct 6, 2026, and its bulletin says "The revised variance form must be completed and included when the variance is registered through OVP." An Appendix 1 application would have to be re-keyed before an officer could register it. Part 1 has the same four sections on both forms, and the two differ in six places: the Section B checkbox wording, the Section D columns, the privacy and acknowledgement block, and the wording of Part 2(a), Part 2(b) and Part 3. We map them field by field and never sign, declare or fill an officer field. An Appendix 1 export would be a second field map and is roadmap, to be built only if the judges ask for it. The list of differences is in `docs/implementation-plan.md` §4.3.

**17. How has testing informed the design, and how will it inform the final version?**
Not yet through people. So far we have automated tests and an agent-run browser walk, and they pin the safeguards: the quote check, a commit rule that stays empty until calibrated, a labelled fallback, and a property test with a lying model. We have not run a session with an applicant or an officer. The next step is Round 1 with three first-time applicants (one homebuilder, one general contractor, one manufacturer), then Round 1b with one or two officers on a package with planted gaps, then a retest after fixes. Each round has targets fixed before the session and names the design decision it changes (`docs/implementation-plan.md` §7.2).

**18. Does it name the benchmark acceptable solution, and is each article's rationale consistent with the code's structure?**
That is the design, and part of it is backend. Each code identification result stores a benchmark acceptable-solution record: the quoted Division B sentence the design departs from, a one-line description of the departure, and its objective and function codes by lookup. The deck does not show it yet. Section C rows come from the attribution tables, so each row's rationale follows the code's own structure and not generated text. Each pick also carries a one-line reason from the verifier, which is dropped if it claims compliance or safety (backend), and the code drawer shows the national intent statements as "Why this rule exists". **A written explainer paragraph for each article, which the brief asks for, is not built.** The schema has a field for it and nothing fills it. The Council's deck gives a worked example: Sentence 9.10.15.4.(1), openings in an exposing building face, function F03 and objective OP3.1, and the code database returns the same pair (Table 9.38.1.1., PDF p.1130). Intent statements come from the national NBC 2020 intent statements, which are not Alberta law, and the screen labels them explanatory only. Where a lookup has no row, the cell says so and is not filled.

**19. How does it know where to stop, and when is engineering required?**
A deterministic check over confirmed facts answers "required", "depends" or "no", and it cites the Division C rule when one applies, for example 2.4.1.1.(3) and 2.4.1.2.(1). Missing facts never produce "no". The review screen shows the callout "An engineer or architect is required for Section D" with the line "Batatis can list what that evidence must address, but it can't write it." It never writes a professional opinion, a test result or an engineering judgment, and the cards for risk, mitigation and assumptions say that the applicant writes them. The agreement figures for the flag are in question 2 and carry the same limits. Sources: `research/facts/professional-involvement.md` (the rules, with PDF pages), `engine/professional.py`, and the lookups in `docs/research/2026-10-21-source-checks.md` §7.

**20. How does it signal its own confidence instead of filling boxes?**
Every fact carries a status and its source, and only confirmed facts are written to the exported form. Missing or unconfirmed information shows as a named gap with a question. A field shows N/A only when the applicant has confirmed that it does not apply and given a reason, and a blank is never shown as N/A (backend, with no screen for it yet). "Not sure" never blocks and becomes an open question for the officer. The "Official PDF" (the Council's own form filled in, which the Council does not issue or approve) stays locked, with reasons, until a current check finds no required item missing. Code identification commits nothing automatically, because the commit rule needs a calibration file from the benchmark and none exists. The intake reader gives each fact a pointer to its source words and the deck shows the fact beside them for the applicant to confirm, and two different values for one field give a question and no fact.

**21. Could a first-time manufacturer, contractor or homebuilder use it unaided?**
We do not know, because no real applicant has tried it. Onboarding sets the applicant type, which changes the prompt on the Describe screen and whether the planner asks about scope. Every card says why it asks, and the flow shows one question at a time. Three fictional demo cases, one per type, are ready as test inputs (`evals/demo-cases/`). What would measure it is the Round 1 target: at least 2 of 3 first-time applicants finish Part 1 without help in a time set from our internal dry runs. That needs real participants and is not scheduled.

**22. Would a design lead choose this over their current process?**
Unknown. Today the alternative is to prepare the form and the Division C documentation by hand or to pay a consultant, and Alberta publishes no consultant price to compare. Our bet is that arriving complete, with every citation traceable to the code text and a clear list of what is missing, is worth more than a blank form. We would measure it in a pilot by comparing returns for more information against the organization's baseline, and by whether applicants come back for a second package.

**23. How do you know your code references are real?**
Every article the verifier picks must carry a word-for-word quote, and the quote is checked against that article's text in our NBC(AE) 2023, 2nd-printing database. A pick whose quote does not match is dropped, never repaired. The code database is built by script from the official PDFs and checked against SHA-256 hashes, and a fixed-seed audit of 30 provisions found 0 mismatches. In our documents we quote provisions as the Code prints them, with the PDF page. For example, Division A, Clause 1.2.1.1.(1)(b) (PDF p.38) reads: "using alternative solutions that will achieve at least the minimum level of performance required by Division B in the areas defined by the objectives and functional statements attributed to the applicable acceptable solutions". Sentence 1.4.1.1.(4) (PDF p.41) says that wherever the Code refers to alternative solutions, they are the ones in that clause.
