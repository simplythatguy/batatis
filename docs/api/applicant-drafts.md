# Applicant drafts

Batatis drafts the applicant's explanations. It does not produce professional analysis, calculations, test results, opinions of equivalence or seals. Draft acceptance records the applicant's ownership of the wording, not a technical finding.

## Stored contract

`Case.drafting` stores the latest drafting record, including its source snapshots, input fingerprint, generation metadata, registry searches, notices and draft history. It is separate from `Case.facts`, Section C attributions and supporting evidence. Reading a case never generates writing.

- `POST /cases/{id}/drafts` takes `{expected_version}` and produces the writing from the saved description, latest source facts, readable owned document pages, confirmed provision text and deterministic Section C, reviewer guidance and precedent structures. It returns the full saved Case.
- `POST /cases/{id}/drafts/{draft_id}/decision` takes `{expected_version, decision: "accept" | "reject"}` and returns the full saved Case. Acceptance and rejection use compare-and-swap, enforce applicant edit access and reject stale input. Neither accepts client-authored draft text or sources.
- `GET /cases/{id}/drafts` returns the record with current staleness, without provider requests; it returns 404 before the first successful generation.

Each draft has `id`, `field`, `title`, `text`, `claims`, `questions`, `status` (`draft`, `accepted`, `rejected`), and decision metadata. Fields are `alternative_description`, `process.rationale`, `process.risk_assessment`, `process.mitigating_measures`, `process.assumptions_and_limits`, `process.maintenance_operation`, `process.qualifications`, `section_c.<provision_id>.explanation`, and `evidence_plan`.

Each claim has `text`, `kind` (`fact`, `assumption`, `plan`) and `sources`: exact `{source_id, quote}` references into the record's `sources`. A source snapshot identifies its kind, reference, page where applicable, label, text, metadata and optional public URL. Personal details are redacted before model use; quotations are checked against the saved source snapshot. Owned file identifiers, page numbers and file hashes retain the connection to the original document. Canonical code text is preserved verbatim. Assumptions remain visibly labelled; requested work is a plan, never a report of completed work. Missing facts are explicit questions with `text`, `why`, `routed_to` (`applicant` or `professional`) and cited sources, rather than fabricated prose or placeholders. A question-only piece has no wording to accept.

On acceptance, the server writes one confirmed applicant-owned fact at the draft's canonical field, with `kind: "pointed"`, `source.type: "user_click"`, `source.ref: "applicant-draft:<draft_id>"` and `source.quote` equal to the accepted text. The retained draft preserves claim-level provenance and the original generated wording. Section C lookup rows and evidence completion never change as a consequence of accepting writing. Rejection writes no answer. Repeated decisions are idempotent; a contrary decision requires a new draft. Decisions name server-owned draft IDs; they never accept replacement text from the client.

Accepted or manually written answers are protected from generation. The exception is verified rough Section B wording automatically extracted by intake: `replaces_fact_id` identifies exactly that old fact, and an explicit acceptance appends the new answer under the same version check. The original fact remains in the ledger. A later manual answer prevents this replacement.

Generation excludes prior generated/accepted draft prose as evidence for new claims. `generated_texts` is an append-only record of every generated passage (whole drafts and single claims), including pending drafts that a later generation replaced. A fact or document page that repeats one of those passages is excluded as a source. The only exception is a passage listed in `source_history`, the record of the original facts, descriptions and document pages (matched by file hash) that earlier generations read. When a later description withdraws or changes a passage, facts read from the old passage stop being sources. An applicant's direct answers are unaffected. A fingerprint binds drafts to input facts, confirmed provisions and owned document bytes; regeneration does not silently overwrite accepted answers. Provider errors, unread pages, truncated context and registry fallback are explicit. A registry match is a discovery lead requiring a scope/status/edition check, never product acceptance or evidence of project equivalence.

## What drafting needs

The current flow starts with the saved project description and any uploaded PDFs. It reads the actual owned pages, rather than relying only on extracted fact summaries. Statements read from manufacturer literature, draft letters and fictional or historical examples keep their qualifications. Conflicting or missing information becomes a question; it does not become a settled property, appointment, measure or test result.

Section C explanations require confirmed benchmark provisions. Their text and objective/function/intent rows come from `Codes` and `section_c_rows`; drafting neither discovers articles nor writes attributions. Without confirmed provisions, other drafts can describe the proposal and ask for the unresolved benchmark. The professional screen controls whether the wording may state a professional requirement or must leave it conditional.

All six narratives reuse `process_fields` reviewer guidance and `process_examples` structure descriptions. Precedent structures guide the shape of the explanation; their project facts, outcomes and historical editions do not become this project's evidence. Proposed comparison methods, mitigation work and maintenance arrangements remain plans or assumptions until the applicant supplies or accepts them. Authentic professional deliverables remain separate requirements.

The generator receives source IDs and exact excerpts. The server validates the requested fields, quotation membership, allowed article identifiers, numerical sourcing and prohibited verdicts. A second model call checks the full claims and questions for entailment, project specificity and the professional-work limit. Failed or incomplete validation saves no partial batch. This is model checking, not professional or human verification.

Hosted generation and the semantic auditor use the configured metered Sol connection; desktop uses the existing leased workflow connection and its supported profile. The live switch, account access and spend controls apply. No provider connection means no generated writing. GET, open and refresh never incur generation or registry requests.

Sources are bounded to 30 owned files, 60 pages per file, 16,000 characters per source and 150,000 source-context characters. Notices identify omissions, unread pages and truncation. Registry discovery uses at most three source-derived name queries and five results per query. `registry_queries` retains the exact source span used for each query; `registry_searches` retains the actual response, live/snapshot provenance, dates and limitations. Neither a match nor a negative search proves applicability or current project acceptance.

## Adjacent threads

The application workspace may render, edit or highlight `claims` and source references. An edited answer remains applicant text and must retain its relation to the draft if it is presented as a revision. `accepted_fact_id` binds the original accepted wording to the ledger; later editing must not rewrite its historical source record. The exact wire shape is owned by `engine/models_drafting.py`; run `python -m engine.schema_export` and `npm run gen:types` in `web` after model changes.

The question flow can consume `engine.drafting_questions.open_questions(case)` without adopting this thread's presentation or ordering. Each unresolved item exposes the originating draft, canonical draft field, question text, reason, sources and responsible role. Stable answer fields are `drafting.questions.<draft_id>.<zero-based index>`; stable gap IDs are `draft-question:<draft_id>:<index>`. A confirmed pointed answer must have `value == source.quote`, just like other applicant text. Unknown or withdrawn answers do not resolve the question. Accepting wording creates no question answer. Unresolved questions on current accepted wording remain blocking administrative gaps; changing the governing answer or withdrawing its code scope retires obsolete questions while preserving history.

Finding codes continues to own provision discovery/selection; drafting only reads the confirmed selection and deterministic lookup results. Accepted B and process wording use the existing canonical export paths. Accepted C explanations and the evidence plan appear as separate appendix text; they do not alter Section C attribution rows, attach reports or close professional/evidence requirements.

The Review stage supplies one shared panel with a piece selector, claim sources, explicit questions, accept/reject controls and guidance disclosure. Relevant question cards link to that same panel. Writes share the existing save queue and protect newer local edits, account changes and submission transitions. Read-only, signed-out, question-only, stale and failed states have explicit controls or explanations. This adds no rewriting editor and changes no question-order policy.

The evaluation method and its input isolation are documented in `evals/drafting-protocol.md`. Passing scripted transports proves mechanics; live writing quality requires the separate provider evaluation.
